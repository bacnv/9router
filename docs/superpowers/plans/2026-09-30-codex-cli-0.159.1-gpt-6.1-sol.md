# Codex CLI 0.159.1 + GPT-6.1 Sol — 9Router patch

**Date:** 2026-09-30
**Branch:** `merge/v0.5.91-fci-ai`
**Commits:** `9be4abeb` → `1654db0f` → `428fce76`
**Tag:** `v0.5.91-fci-ai.4`

This document covers the **source patch to 9Router only**. Installing or upgrading the
`codex` binary itself is out of scope — the gateway never runs it, it only impersonates
its identity headers upstream.

## Why

Codex CLI 0.159.1 introduced `gpt-6.1-sol`, ranked first in its embedded model catalog.
9Router did not know the id, so `cx/gpt-6.1-sol` failed validation and never routed. The
gateway also advertised version `0.155.0` to OpenAI's backend, five releases behind.

The catalog lives inside the release binary, not the npm package (the npm tarball is a
launcher stub). Extract it with:

```bash
npm pack "@openai/codex@0.159.1-linux-x64"     # ~160 MB
tar xzf openai-codex-*.tgz
BIN=package/vendor/x86_64-unknown-linux-musl/bin/codex
strings -n 8 $BIN | grep -n '"slug"'           # line number per model object
strings -n 8 $BIN | sed -n '<line>,<line+200>p'
```

Relevant fields for `gpt-6.1-sol`: `visibility: "list"`, `priority: 1`,
`use_responses_lite: true`, `tool_mode: "code_mode_only"`, `minimal_client_version:
"0.153.0"`, context 272k / max 872k, and effort levels `low`…`max` plus `ultra`.

## Patch

### 1. `open-sse/providers/registry/codex.js` — version bump

```diff
 // Codex CLI version seen by OpenAI's backend — single source for the Version /
 // User-Agent identity headers. Bump when the installed codex CLI is upgraded.
-const CODEX_CLI_VERSION = "0.155.0";
+const CODEX_CLI_VERSION = "0.159.1";
```

This constant is the **entire** upgrade. It feeds, in one place:

| Consumer | Location |
|---|---|
| `User-Agent: codex_cli_rs/<v>` | `registry/codex.js:45` |
| `version: <v>` request header | `registry/codex.js:46` |
| `cliVersion` on the flattened provider | `registry/codex.js:42` |
| Image-generation User-Agent + `version` | `handlers/imageProviders/codex.js:8,175` |
| Connection-test headers | `src/app/api/providers/[id]/test/testUtils.js:31` |

Nothing else needs touching. `open-sse/config/appConstants.js:11` re-exports it for the
non-registry consumers.

### 2. `open-sse/providers/registry/codex.js` — add `gpt-6.1-sol`, pin `gpt-6-luna`

```diff
   models: [
+    // Codex 0.159.1's catalog ranks this first (priority 1), so it leads the list.
+    // The catalog also advertises "ultra", but that level auto-delegates to subagents —
+    // a transport the gateway does not carry — so it stops at "max" like its siblings.
+    { id: "gpt-6.1-sol", name: "GPT 6.1 Sol", responsesLite: true, thinkingLevels: GPT_6_LITE_THINKING_LEVELS },
     { id: "gpt-6-astra", name: "GPT 6.0 Astra" },
     { id: "gpt-6-sol", name: "GPT 6.0 Sol", responsesLite: true, thinkingLevels: GPT_6_LITE_THINKING_LEVELS },
-    { id: "gpt-6-luna", name: "GPT 6.0 Luna", responsesLite: true, thinkingLevels: GPT_6_LITE_THINKING_LEVELS },
+    // Luna is pinned to a single effort: its catalog offers only "max" as usable here,
+    // so every requested level collapses to it.
+    { id: "gpt-6-luna", name: "GPT 6.0 Luna", responsesLite: true, thinkingLevels: ["max"] },
```

Four decisions worth recording:

- **`responsesLite: true` is mandatory, not cosmetic.** Every `gpt-6*` arm carries
  `use_responses_lite: true`. Without the flag the request goes out in the wrong shape:
  no `x-openai-internal-codex-responses-lite` header, no `additional_tools` prefix, and
  the model sees no tools at all.
- **Effort levels are per-model — do not trust the `*gpt-6*` glob.** The pattern entry in
  `providers/thinkingLevels.js` yields `none`/`minimal` and omits `ultra`, which matches
  none of the gpt-6 arms. Levels must be declared explicitly.
- **`ultra` is deliberately withheld.** It means automatic subagent delegation, a
  transport the gateway does not carry. The list stops at `max`; an incoming `ultra` is
  downgraded by the existing fallback.
- **`gpt-6.1-sol` leads the array, so it becomes the `cx` default.** `getDefaultModel()`
  returns `models[0]`. This matches the catalog's own priority-1 ranking, and changes the
  default from `gpt-6-astra` — which affects `src/app/api/providers/validate/route.js`
  and the provider connection test.

### 3. `open-sse/executors/codex.js` — coerce single-level models

```diff
 function normalizeReasoningEffort(model, value) {
   const supportedLevels = getThinkingLevels("codex", model);
+  // A model pinned to one level (e.g. gpt-6-luna → ["max"]) takes that level no matter
+  // what the client asked for, so an unsupported effort can never reach the upstream.
+  if (supportedLevels?.length === 1) return supportedLevels[0];
   if (supportedLevels?.includes(value)) return value;
   if (isCodexResponsesLiteModel(model) && (value === "none" || value === "minimal")) return "low";
   if (value === "ultra" && supportedLevels?.includes("max")) return "max";
```

Declaring `thinkingLevels: ["max"]` alone changes only what the dashboard **advertises**.
The function previously ended in `return value`, so a client calling the API directly with
`low` would still forward `low` upstream. The guard fixes that, and is keyed on the
*count* of levels rather than a model name, so any future single-level model inherits it.

Side effect to be aware of: Luna's `none` now resolves to `max`, not `low`. The pin runs
first by design — a single-level model has exactly one answer.

### 4. Tests

- `tests/unit/codex-gpt6-lite.test.js` — new `Codex GPT-6.1 Sol` and `Codex GPT-6 Luna
  single level` blocks; assert the registry entry, the level list, the coercion across
  `low`/`medium`/`high`/`xhigh`/`max`/`ultra`/`none`/`bogus`/absent, and the outbound
  lite shape via a mocked `proxyAwareFetch`.
- Two pre-existing tests used Luna as an incidental fixture for *other* behaviour (native
  lite passthrough, `none → low` clamping). The pin broke them, so they now use
  `gpt-6-sol`, which exercises the same code paths without the pin interfering.
- `tests/__baseline__/providers-baseline.json` — three codex lines
  (`cliVersion`, `User-Agent`, `version`). **Hand-edit these.**
  `tests/__baseline__/snapshot-providers.mjs` regenerates the whole file and will
  otherwise sweep in unrelated pre-existing drift (claude `profileUrl`/`resetUrl`, a
  `tokenharbor` key reorder).
- `tests/unit/image-generation.test.js` and the `version` assertion in
  `codex-gpt6-lite.test.js` read `CODEX_CLI_VERSION` instead of a literal. Four
  image-generation tests were already red on a clean v0.5.91 checkout for this reason.

## Verification

```bash
cd tests
npx vitest run unit/codex-gpt6-lite.test.js unit/image-generation.test.js unit/codex-auto-review-routing.test.js
node __baseline__/verify-providers.mjs      # must print "byte-for-byte equal"
node __baseline__/verify-alias.mjs
node __baseline__/verify-oauth-urls.mjs
```

The full suite is never green on a clean checkout, and `verify-no-regression.mjs` cannot be
trusted outside the Docker image it was written for: it splits test paths on `/app/`, a
container path, so on a bare checkout every path collapses to `undefined :: …`, nothing
matches `known-fails.txt`, and it reports dozens of phantom regressions. `known-fails.txt`
is also incomplete — it catalogues 24 of the ~98 failures a clean v0.5.91 tree produces.

Judge a change by **diffing the failure set** against a clean worktree at the same commit:

```bash
git worktree add /tmp/clean --detach <pre-patch-sha>
# symlink node_modules and tests/node_modules in — `cp -al` fails across devices
cd /tmp/clean/tests && npx vitest run --reporter=json --outputFile=/tmp/clean.json
# then compare the failed (file, testName) pairs of both runs
```

Observed on this patch: 46/46 codex tests pass, the three baseline verifiers are green,
`npx eslint` reports 0 errors, and `npm run build` succeeds. The full suite goes from
**98 failures on a clean pre-patch checkout to 94** on the patched tree — 0 regressions,
and the 4 image-generation tests that were red come back green.

## Out of scope

- Installed `codex` binary, and any deploy/build step.
- `gpt-daybreak-blue-latest` / `gpt-daybreak-red-latest` — present in the 0.159.1 catalog
  but `visibility: "hide"` with `model_specialty: "cyber"`. The codex registry has no
  hidden-model mechanism, so adding them would surface them in the dashboard.
- `gpt-6-sol`'s catalog advertises `ultra`, but it is not currently listed. Pre-existing,
  left as-is.
- No `-review` variants: the `gpt-6` family has none, unlike `gpt-5.6`.
